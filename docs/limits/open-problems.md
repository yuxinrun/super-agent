# 还没解决的问题

一篇把架构讲得漂亮的文章，最容易在最后一节偷懒。这篇不能也偷懒——**所以先把话说清楚：下面前四条是 DeepSeek 自己承认的，后三条是本站推演。**

## 官方自己列的四条

| 未解问题 | 卡在哪 | 为什么这条最难 |
| --- | --- | --- |
| 架构扩展性 | Worker 数量上去以后，路由、状态、成本三样同时涨 | 现在的数据来自一个内部实例，不是几百个团队共用 |
| 人机协作效率 | 人怎么打断、怎么改主意、怎么只验收不看过程 | 「异步全双工」这件事在协议上说了，但**默认还没开** |
| 跨实例通信（A2A） | 你的 Agent 和我的 Agent 能不能直接说话 | 一旦能说话，鉴权、租户边界、责任归属全部重来 |
| 安全与隐私保护 | 一个持续在线、能读你群聊和 CI 的东西 | 它的攻击面不是某个漏洞，是**它能看到的所有东西** |

::: warning 关于「异步」的措辞
文章里提到异步 ReAct Loop 可以让 Agent 在任务进行中接收新指令。但同时说明：**这个能力目前不是默认开启的。**

这很重要。「架构上支持」和「你现在能用」之间，隔着一整个产品周期。
:::

## 三条官方没写、但迟早要还的账

### 01 静默成本的归属

「投机执行」很好：看到 bug 先静默复现，能修就修，不能修就不吭声。问题是**不吭声的那部分也算钱**。

一个 Worker 花二十分钟复现一个最后没能修的 bug，这笔账记在谁头上？没人问，也没人知道发生过。当这类尝试一天三百次，成本会以一种**没有任何人会看到的报表**的方式流走。

任何真要上这套东西的团队，都需要给静默路径单独一条预算和一个开关。

### 02 看门狗该有多大权限

Watchdog 的判断方式很聪明：不只看心跳，还用模型判断「这个 Worker 是不是在瞎忙」。

但**判断和纠正之间有一条线**。一个认为「你在跑偏」的看门狗，应当被允许杀掉任务、改写目标，还是只能记录一行日志？

给它权力，就多了一个可能误判的、会动的东西；不给它权力，它只能报警，而报警最终又会变成那个「93% 不是活的消息流」的一部分。

::: tip 这条没有好答案
操作系统面对这个问题用了四十年：内核有绝对权力，但内核的每一个决策都是确定性的、可复现的。用一个概率模型做看门狗，等于把一个**非确定性的判断**放进了**必须确定性的位置**。这是整个设计里我最担心的一块。
:::

### 03 谁审计它

一个持续在线的 Router，它是所有事件的必经出口，它读过你的群聊、你的 CI、你的日程。它同时也存着完整的外部状态链。

这套架构把「记忆」从模型窗口里搬进了数据库——**搬对了**。但它也就顺手把「审计需求」从会话日志级别，提到了数据平台级别。一个能替你干活的系统，和一个能看见你全部工作痕迹的系统，是同一个东西。

## 一条实践层的边界

除了上面这些设计层面的开放问题，还有两个特别不性感但特别真实的：

- **接入渠道有限。** 现阶段能被接进来的就是那么几类事件源。
- **个人部署有技术门槛。** 无状态容器 + 数据库 + 本地 daemon，这套东西不是一个 `npm install` 能解决的。

<div class="mp-quote">一个诚实的信号经常藏在结尾：这套设计没有假装自己已经解决了所有问题。它给的是一个还在往那儿走的形状。</div>
