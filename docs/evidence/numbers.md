# 实验数字怎么读

一篇讲架构的文章里最容易骗人的就是数字。所以这篇先把实验怎么做的讲完，再讲数字，最后讲**这些数字没证明什么**。

<MetricGrid />

## 实验是怎么摆的

DeepSeek Harness 团队做了一次端到端对照。不是「给模型一道题看它答得多快」那种 benchmark，而是把 Agent 扔进一个**真实的工作流噪声**里。

| 设置项 | 内容 |
| --- | --- |
| 输入 | 群聊消息流 + GitHub CI 消息流，两条一起灌 |
| 单次运行规模 | 约 300 条消息 |
| 其中真正的活 | 约 20 个工作请求 |
| 剩下的 | 闲聊、追问、叫停、CI 通知 |
| 对比方案 | 四套端到端配置 |
| 重复次数 | 每套跑 5 次 |

那个「20 / 300」的比例是整组实验最值得看一眼的地方。**93% 的消息不是活。** 而这恰好就是真实工作现场的样子：你一天里大部分消息不需要你动手，但每一条都在抢你的注意力。

一个只会「收到一条处理一条」的 Agent，在这种负载下的表现，就是被 280 条噪声打断 280 次。

## 主结果：不是快，是尾巴短

| 方案 | p50 | p95 |
| --- | --- | --- |
| Super-agent | 12.4 分钟 | 15.7 分钟 |
| 单 Session + Subagent（旧方案） | — | 29.5 分钟 |

::: tip 先看清这两个百分位是什么
p50 是中位数：一半任务比它快。p95 是第 95 百分位：**最倒霉的那批任务**在哪。

看这组数字，重点是**两者之差**。Super-agent 的 p50 和 p95 只差 3.3 分钟，意味着它交付得**整齐**；旧方案的 p95 是 29.5 分钟，是最长链条那一截。

工程上真正折磨人的从来不是平均耗时，是「为什么这个任务卡了半小时」。所以这里最该记的不是 12.4，是 15.7 对比 29.5。
:::

## 最有意思的一条：给了子任务工具，模型不用

旧方案里其实**配了 Subagent 工具**——也就是说「派活给别人」这个能力一直在它手边。

结果是：中性提示下，**五次运行，一次都没有调用过 Subagent。**

后来团队换了一个「倾向于委派」的提示，五次里有四次开始派活了。可即便这样，整条链路还是比 Super-agent 慢。而且有一次，模型主动拒绝委派，理由是**这个活太小，我自己来**。

::: warning 这条的杀伤力
它同时说明两件事：

1. **「能并行」和「会并行」是两回事。** 把工具放上，不等于模型会用它。
2. **把调度交给模型的临场判断，等于把架构交给心情。** 一个「觉得这活太小」的自我判断，就能让整条并行路径失效。

Super-agent 的思路不是「劝模型去委派」，而是**从结构上让它没法亲自下场**——Router 手上一个工具都不给。详见[双层架构](../architecture/two-layer.md)。
:::

## 消融实验：省的不是秒，是钱

把「订阅直通」（Worker 订阅 Thread 后，后续事件不再经过 Router 判断）这条捷径拆掉，重新跑：

| 指标 | 变化 |
| --- | --- |
| 完成时间 | 基本没动 |
| Router 判断次数 | 增加约 30% |
| 缓存读取 token | 2323 万 → 3177 万（约 +37%） |

这是一个非常干净的结论：**直通省的不是时间，是成本和主管的带宽。**

如果你只看 p50，会觉得这条设计可以删。翻开账单才知道它一直在替你挡掉什么。

## 批处理：唯一一个单独拎出来的优化

Router 不是来一条事件想一次，而是**攒一小批一起想**。单条决定的推理时间从 **6.4 秒降到 1.6 秒**。

这也是典型的操作系统手法：固定的高开销动作（这里是「叫醒一次大模型」）尽量摊给一批请求。四个字母的优化，四倍收益。

## 这些数字没证明什么

诚实的部分放在最后。

1. **一个场景，五次重复。** 300 条消息的群聊 + CI 是一个很具体的负载。换成「1000 条工单」或「纯代码库重构」，曲线不一定长这样。n=5 给的是一条趋势，不是一个置信区间。
2. **只量了时间，没量质量。** 这组实验里没有「交付物好不好」这一项。快不等于对——它证明的是这套架构**在处理噪声时更利索**，不是更聪明。
3. **开源原型 ≠ 跑出数字的那个版本。** 团队自己说了：代码是研究原型，内部实例和公开版本不完全一致。你在 repo 里复现不出这张表，是正常的。
4. **对比对象是「中性提示的单 Session」。** 这是一个诚实但偏弱的基线。真实产品里，很多人已经把提示词、路由规则、多 Agent 框架调得很细了。

<div class="mp-quote">读法建议：把这组数字当成「问题确实存在」的证据，而不是「方案已经赢了」的判决。前者它站得住，后者还需要更多场景。</div>
