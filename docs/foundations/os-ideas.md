# 借自操作系统的七件老主意

DeepSeek 这篇文章最反直觉的一点：**它没有提出任何新理论，并且把这当作优点。**

团队明确说，这套设计是把计算机系统里的经典思想搬进 Agent 架构——调度、缓存、批处理、Fast/Slow Path、投机执行、存算分离、看门狗。这些东西加起来有五十多岁，比整个机器学习工业界都成熟。

<BorrowGrid />

## 为什么「偷师系统软件」是对的方向

因为 Agent 现在遇到的问题，**系统软件早就遇到过，而且解决得不错**。

| Agent 的处境 | 系统软件的同一幕 | 已经存在的答案 |
| --- | --- | --- |
| 一个模型要同时管很多件事 | 一个内核要管很多进程 | 调度器、优先级、抢占 |
| 上下文窗口太小、太贵 | 内存太小、太贵 | 分层存储、换页、工作集 |
| 每条消息都想一次，成本高到不能接受 | 每次中断都全量处理 | 批处理、快路径/慢路径 |
| 不知道任务是不是还活着 | 不知道进程是不是死了 | 心跳、看门狗 |
| 想在被确认前先做点准备 | 分支未定时先算 | 投机执行 |
| 记忆不能绑在进程上 | 数据不能绑在应用服务器上 | 存算分离 |

这不是修辞上的相似，是**同构**：约束条件一样（稀缺资源、不可预知的到达、必须容错），所以解法可以直接搬。

## 熟悉的人一眼就看出来了

::: tip 内核态与用户态
Router 只做调度、手上没有工具；Worker 只做事、不直接对外沟通。这个分工和操作系统里内核态负责调度、用户态负责计算几乎是同一个图形。

搬过来的不是某个具体算法，是一种**思维习惯**：先划分职责和权限，再谈智能。一个「什么都能做」的 Agent，等价于一个「什么都能干」的进程——你无法推理它，也无法保证它。
:::

## 「不性感，但好使」的价值

技术圈偏爱新词。但这次发布里最耐读的一件事恰恰相反：**它证明了年轻领域可以心安理得地抄老领域的作业。**

三条可以从这里搬走的经验：

1. **别为你没有发明什么而道歉。** 你的用户只关心问题有没有被解决。
2. **成熟的解法自带工程红利。** 用「缓存分层」描述上下文预算，团队之间沟通成本立刻下降——因为听的人早就知道这层该怎么设计、怎么失效、怎么度量。
3. **老思想给你免费的度量指标。** 批处理有摊薄倍数，缓存有命中率，看门狗有心跳间隔。一旦你借用框架，你就自动借用了它的 KPI，不用自己发明。

<div class="mp-quote">Agent 领域最缺的不是想象力，是纪律。系统软件有五十年的纪律，抄它不丢人。</div>

## 一个必要的提醒

::: warning 类比不保证正确
「像操作系统」意味着**问题形状相同**，不意味着**解法可以直接照搬**。操作系统面对的是确定性的指令流；Agent 面对的是一个会误解题意、会自己决定要不要听话的概率模型。同一套分层，两边需要完全不同的容错设计。

具体证据就在实验里：模型在配置了 Subagent 工具的情况下，中性提示下**五次都没委派**。操作系统可不会「觉得这个活太小我自己来」。（见[双层架构](../architecture/two-layer.md)）
:::
