# 面向人的交互：换个渠道找它，还是同一个 Agent

这一层解决一个非常具体的问题：**人和 Agent 之间的对话，不应该只有一个入口，也不应该是排他的。**

## 多信道：一个 Agent，很多扇门

Super-agent 的「连续」特征在这里落地——你可以在 IM、GitHub 评论等不同信道与**同一个** Agent 交互。

| 信道 | 你在那里说什么 | 系统要解决什么 |
| --- | --- | --- |
| 群聊 / IM | 「这个投诉帮我分个类」 | 消息身份识别：这句话是给它的吗？属于哪个 Thread？ |
| GitHub 评论 / PR | 「顺手看下这个 CI 为什么挂了」 | 事件与代码上下文的关联 |
| 邮件 / 日程 | 「下周这个会帮我准备材料」 | 时间维度的任务唤醒 |
| CI 结果 | 没人说话，只是构建红了 | 无人发起的 Trigger 如何进入队列 |

关键在于：**信道只是入口，不是身份。** 你在群里问的那件事，和在 PR 里问的那件事如果是同一个 Thread，它就应该是同一份记忆，而不是两个互不相干的会话。这正是把状态放到模型外面才能做到的事（见[存算分离](./storage-compute.md)）。

::: tip 为什么这比听起来重要
今天的现实是：你在工具 A 里问 AI 的东西，和工具 B 里问的，永远不共享记忆。所谓「多渠道」在多数产品里等于「多个互不认识的机器人」。Super-agent 把入口收敛到 Router：所有信道汇到同一个协调点，背后有几个 Worker 是你的实现细节，不是你的认知负担。
:::

## 全双工：它干活时，你不用排队

传统 Agent 循环是个半双工对讲机：它开始执行，你就只能等；你要说点什么，通常意味着打断。

Super-agent 引入 **异步 ReAct Loop**——推理（Reason）与行动（Act）的循环不再阻塞对话通道，让 AI 在执行耗时任务时**仍能响应新指令**。

不过这里必须诚实：**这个能力在原型里尚未默认开启。** 它是设计目标，不是已完成路径。所以「它跑着呢但你随时能插话」这句话，现阶段应该读成「架构给这件事留了位置」。

<div class="mp-quote">把还没默认打开的功能说清楚，是技术文章和产品公告最大的区别。这次它做得算老实。</div>

## 投机执行：先干，确认有用再交

「主动」这个特征最有意思的实现细节在这里。它借的是 CPU 的老主意：**结果是否会被采用还不确定时，先在后台试着做，有用就提交，没用就丢掉。**

文章给了两个具体策略：

<div class="mp-split">
<div>

### 研发场景：静默复现并修复

有人在群里反馈一个 bug 时，AI **先在后台复现、分析原因**；只有确认问题真实存在、并且找到了简单的修复方式，才向人提交结果。**否则保持安静。**

这是投机执行的教科书式用法：绝大多数 bug 反馈不值得立刻打扰你，但其中一部分值得你已经动手查过。

### 个人助手场景：会议邀请

收到一个会议邀请后，它可以提前核对日程冲突、搜集背景资料、备好回复草稿。等你真问起时，答案已经在了。

</div>
<div>

### 代价清单：这套机制的三张账单

| 账单 | 说明 | 你需要决定的事 |
| --- | --- | --- |
| **算力** | 做了可能全丢掉的工作 | 愿意浪费多少预算换响应速度 |
| **副作用** | 「先试着做」在有写操作的世界里很危险 | 哪些动作可以被投机，哪些绝对不能 |
| **打扰** | 提交时机判断错，就是噪音 | 什么条件下才允许它开口 |

第二张账单最重。读文件、查资料可以随便投机；**改代码、发消息、下订单不行**。一个会把投机执行用到写操作上的 Agent，不需要多聪明就能造成真实损失。

</div>
</div>

::: warning 站内提醒：投机执行不是「随便先做做」
判断标准只有一条——**这个动作做错了，你能不能无痕撤销？** 能，就允许投机；不能，就要求显式确认。这条规则应该写进权限层，而不是写进提示词（理由见[双层架构](./two-layer.md)里那个五次没委派、以及「模型嫌活小自己上手」的实验）。
:::

## 这三件事合起来是什么

把「一个入口之外的很多扇门 + 不用排队 + 会提前准备」叠起来，得到的就是团队想描述的那种体验：**Agent 从工具变成长期在线的协作者。**

你不再「打开一个 AI」，你在某个已经存在的通信渠道里对一个同事说话，它可能正在忙别的，但它知道这件事是谁的、要做什么、并且会在合适的时候回来找你。
