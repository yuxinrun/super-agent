# 计算、状态与环境分离：把记忆从模型里搬出去

这一层是最不像「AI」、最像**系统工程**的一层，也是这套架构能不能常驻的真正决定因素。DeepSeek 直接在文章里点明了灵感来源：数据库领域的**存算分离**。

它发生在两个尺度上，别混为一谈：

| 尺度 | 分离什么 | 机制 |
| --- | --- | --- |
| **窗口尺度** | 「现在给模型看什么」vs「先存着以后再说」 | Inline & Spill、链式召回 |
| **部署尺度** | 「推理在哪跑」vs「状态存哪」vs「环境在哪」 | 云端 Agent Loop + 数据库 + 本地 daemon（BYOM） |

## 窗口尺度：Inline 与 Spill

模型的上下文窗口就是那个唯一的工作台，桌面只有这么大。团队的做法是明确的两级：

- **Inline**：近期可能用到的信息**直接放进上下文窗口**，让模型抬眼就能看到。
- **Spill**：超出预算、或使用频率低的内容**留在窗口之外**，供模型按需读取。

这就是操作系统的内存/磁盘分层，被原封不动搬进来了：热数据在快地方，冷数据在便宜地方，访问时再换入。

::: tip 消融实验给这条设计标了价
把事件直通机制拆掉之后，读缓存 token 从 **2323 万涨到 3177 万**（约 +37%），而完成时间基本不变。这组数字说明的不是「慢」，而是「**把内容全部塞回模型里，是要单独付钱的**」。上下文预算是成本项，不是风格偏好。
:::

## 引用尺度：链式召回（Chain of Recall）

Spill 出去的东西要能找回来，否则只是丢掉了。找回的方式不是相似度搜索，而是**沿着引用关系走**：

<div class="mp-steps">
  <div class="mp-step"><b>1</b><div><strong>Trigger</strong><p>一条外部事件进来，它带有来源与身份。</p></div></div>
  <div class="mp-step"><b>2</b><div><strong>Thread</strong><p>事件归属到一条事件线上；这条线是「这件事的上下文」的锚。</p></div></div>
  <div class="mp-step"><b>3</b><div><strong>Worker Session</strong><p>处理这条线的那个会话，与 Trigger / Thread 互相留有 ID。</p></div></div>
  <div class="mp-step"><b>4</b><div><strong>沿 ID 逐级找回</strong><p>模型需要历史时，按关联 ID 一级级把内容读回来，而不是让历史常驻窗口。</p></div></div>
</div>

这套机制的价值在于**它让「记住」不再等于「一直显示」**。跨周存在的任务、跨信道指同一件事、Worker 被换掉之后接着干——都靠这组 ID 关系撑住，而不是靠一个足够大的上下文窗口。

<div class="mp-quote">上下文管理最难的不是压缩，是决定什么可以不常驻还能随时找回。前者是技巧，后者是数据结构。</div>

## 部署尺度：三层各归各位

这是最工程的一段设计。它把三个东西拆开：

| 层 | 放在哪 | 有没有状态 | 为什么 |
| --- | --- | --- | --- |
| **Agent Loop（计算）** | 云端无状态弹性计算容器 | 无 | 可弹性扩缩、可随时重启；**你的电脑睡了，任务也能继续** |
| **会话状态** | 数据库 | 有，这是唯一的真相 | 记忆独立于进程存在，才有连续性与恢复能力 |
| **执行环境** | 用户本地设备，只跑一个**不保存会话状态的轻量 daemon** | 无（设计上刻意） | 命令在本地执行、结果回传；支持 **BYOM（Bring Your Own Machine）** |

最后一行是整套设计里最实用的取舍。真实工作现场在开发者自己的机器上：本地代码库、本地工具链、本地凭证。把环境留在本地、把计算和状态搬上云，同时保证**本地那个进程是个不记事的可抛弃外壳**——重启、升级、掉线都不影响记忆。

::: tip 与「脑手分离」的关系
文章自己做了对照：这个思路和 Anthropic 提出的**脑手分离**（模型推理与执行沙箱解耦）方向一致。区别在落点——那个说法描述的是**托管服务里的按需沙箱**，而 Super-agent 首先要接入的是**用户日常使用、可能间歇在线的个人机器**。同一个原则，两种现实约束：一边解决弹性扩容，一边解决「我的电脑才是干活的地方」。
:::

## 为什么这件事值得单独一章

因为多数 Agent 方案在这里选择了最省事也最脆弱的做法：**把状态放在会话进程里，把记忆放在上下文窗口里**。这样做 demo 很好写，代价是三个致命缺陷：

| 缺陷 | 表现 | 本章的解法 |
| --- | --- | --- |
| 会话即生命 | 进程结束，任务消失 | 状态入数据库，Loop 可重建 |
| 窗口即记忆 | 任务一多就撑爆上下文 | Inline / Spill + 链式召回 |
| 环境即身份 | 换台机器等于换个人 | 本地无状态 daemon，身份在云端状态里 |

所以「持续在线」这四个字，本质是三件很土的工程事情：有一张表存状态、有一层缓存策略决定给模型看什么、有一个可替换的执行壳。**没有一样是模型能力，也没有一样能跳过。**
