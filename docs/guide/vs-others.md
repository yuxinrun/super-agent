# 它和 Multi-Agent 框架有何不同

这是第一个必须回答的问题，否则所有的讨论都会变成「LangGraph 早就这么做了」。答案大概率会让你意外：**它们基本不在同一层，所以既不是竞争，也不是替代。**

一句话版本：

> **框架帮你把「一次任务」编排好；Super-agent 关心的是「一个 Agent 怎么长期活下来」。**

前者是编排层，后者是运行环境层。就像工作流引擎和操作系统——你既可以同时用，也不会觉得它们在抢同一份工作。

## 三个层次，别混在一起

| 层次 | 它在回答什么问题 | 代表 | 有没有生命周期概念 |
| --- | --- | --- | --- |
| 编排层 | 一次任务里，谁先跑、谁后跑、结果给谁 | LangGraph、CrewAI、AutoGen、各类 workflow | 有，但止于本次运行 |
| 会话层 | 一个会话里，模型怎么调工具、怎么派子任务 | Claude Code 的 subagent、各类 agent loop | 会话有始有终 |
| 运行环境层 | 会话怎么跨进程、跨天存在；事件谁来分诊；崩了谁重启 | DeepSeek Super-agent 架构、Harness 基座 | **会话是常驻执行单元** |

Super-agent 全部的新意都在最后那一行。

## 逐条对比

### 与 LangGraph / CrewAI / AutoGen

这些框架允许你定义多个角色和它们之间的消息流——写得很清楚，也能跑出漂亮的结果。但请你注意触发方式：**通常是你发起一次运行**（`invoke` / `stream` / `crew.kickoff()`），运行时建图、执行、返回。运行结束后，那个「团队」就不存在了；下次你重新启动一个。

Super-agent 关心的是相反的方向：如果**没人发起**呢？如果事件在你睡觉时到达呢？如果三件事同时到达，其中两件属于上周没做完的会话呢？这些是框架不会替你回答的问题，因为它们的抽象单位是**图**，不是**进程**。

::: tip 两者可以叠起来用
框架可以是 Worker 内部的实现方式。Router 派下一个「需要多角色协作」的任务给某个 Worker，这个 Worker 里面跑一个 LangGraph 图，完全合理。层次不冲突，冲突的是把它当成同一件事来选型。
:::

### 与 Claude Code / Agent SDK 里的 subagent

这一条更接近，因为 subagent 也是「一个 Agent 派多个 Agent」。差别在两处：

1. **状态住在哪里。** subagent 的产出最终汇回主会话的上下文；Super-agent 把会话状态放到模型外面，Worker 之间不靠同一个窗口共享记忆。
2. **谁在管理会话。** 前者由模型自己（在你的对话里）决定要不要派子任务；后者由一个独立的调度层决定，而且这一层大部分时间不做推理，只走捷径。

结果就是：subagent 让**一次任务**更省你的话；Super-agent 让**一批任务**不需要你在场。

### 与云端「通用 Agent」产品

市面上还有一类异步执行的云端 Agent（给你一个虚拟工作区，交任务，它跑完通知你）。它们和 Super-agent 的目标高度重合——都在解决「人不用全程陪着」。

区别在于交付形态：那些是**产品**，你把任务交给别人运营的运行时；Super-agent 是**架构文本加一个研究原型**，它给的是可以自己搭的那套骨架，以及一份把工程问题讲开的九章文档。前者降低你的部署成本，后者降低你的理解成本。

::: warning 这一条是本站的归纳，不是原文对比
DeepSeek 的技术文章没有点名跟某个产品做 PK。上面的层次划分来自公开报道与常识判断，用来帮你定位这套架构在地图上的位置，**不要当作官方的竞品结论引用**。
:::

## 一张表把所有差别收进来

| 维度 | 编排框架 | 单 Session + subagent | Super-agent |
| --- | --- | --- | --- |
| 触发 | 人发起一次运行 | 人发一条消息 | 事件到达 |
| 生命周期 | 运行结束即消失 | 会话关闭即结束 | 跨会话常驻 |
| 上下文同步 | 图内状态传递 | 全部汇回主窗口 | 模型外部存储 |
| 并行粒度 | 节点 / 角色 | 子任务，仍受主窗口约束 | 独立 Worker，各一份上下文 |
| 崩溃之后 | 重跑这次运行 | 你重发一遍 | 看门狗重启，从断点继续 |
| 谁做调度 | 你写的代码 | 模型 + 你 | Router（多数时候不推理） |
| 你的位置 | 编排工程师 | 全程陪聊 | 定目标 + 验收 |
| 抽象单位 | 图 | 会话 | 常驻执行单元 |

## 为什么这套差别值得单独讲

因为混淆的代价很实际。如果你把 Super-agent 当成「又一个框架」，你会去做一件错事：**试图用它替换现有的编排层**，然后发现它压根不给你写 DAG 的地方。如果你把它当成运行时，你会问第二个错问题：「我什么时候调用它？」

正确的读法是：把它当成一份关于「Agent 常驻化需要哪些零件」的清单。这份清单里，框架提供不了的东西才是重点——事件分诊、状态外置、心跳看门狗、以及**让主管少想几次**的成本工程。

<div class="mp-quote">选型的第一个问题永远不是「用哪个」，而是「它在回答哪个问题」。问错问题，答案再漂亮也没用。</div>
